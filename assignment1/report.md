## 0. 摘要

本作业实现了一个广义五子棋（(m,n,k)-Game）游戏程序与一个遵守
**统一对战协议 v1** 的对抗搜索 AI。AI 以课程讲授的
**MiniMax + Alpha-Beta 剪枝** 为主干，配合四项工程优化：

| 优化 | 作用 |
|---|---|
| **线段索引 + 增量胜负判定** | "是否成 K 连"变成 O(1) 整数比较，搜索内部完全不扫棋盘 |
| **棋型评估函数（增量维护）** | 按长度 K 窗口内双方子数打分，天然表达活 K-1 / 冲 K-1 / 被堵死；权重随 K 自适应 |
| **候选着法生成 + 威胁着法排序** | 有效分支因子从 225 降到 14，剪枝效率显著提升 |
| **迭代加深 + 增长比时限预测** | 在任意时限内稳定返回合法落子，既不顶格用满、也不浪费预算 |

### 1.2 三种对战模式的实现

| 模式 | 入口 | 实现方式 |
|---|---|---|
| **人人对战** | `main_cli.py --mode pvp` / GUI | 两名玩家交替点击/输入坐标，`GomokuGame` 判定胜负与和棋；CLI 支持悔棋命令 `u` |
| **人机对战** | `main_cli.py --mode pve` / GUI 默认 | 人类方由 `HumanPlayer` 接管，AI 方由 `AIPlayer` 包装协议对象；`--human-color` 可选执黑/执白 |

三种模式共用同一个主循环（`game_cli.play_game`），差异只在"参与者对象"：

```python
while not game.is_over:
    player = players[game.current_player]              # HumanPlayer 或 AIPlayer
    move = player.choose_move(game, time_limit)
    game.play(move)
```

`AIPlayer` 负责把游戏状态翻译成协议要求的调用形式，并在返回后**立即校验**：

```python
board = game.board.to_grid()                             # 二维列表副本
last  = game.last_move_of(opponent(self.player_id))      # 对手上一手，首手为 None
move  = self.ai.get_move(board, last, time_limit)
return validate_ai_move(move, game, self.name)           # 越界/占位/非 int → 立即报错
```

这样在自建引擎里就能尽早发现非法返回，而不是等裁判判负。

**GUI 不卡死**：AI 思考放在后台线程，主线程用 `root.after(40, ...)` 轮询结果队列；
AI 抛异常或返回非法坐标都会变成弹窗提示而不是崩溃。
（`smoke_test_gui.py` 用"假弹窗"替换 `messagebox` 后做了无头验证，
覆盖三种模式切换、N/K 预设切换、点击落子、占用格忽略、悔棋、悬停、非法 AI 兜底。）

### 1.3 N 与 K 的配置机制

| 层 | 配置方式 |
|---|---|
| AI | 只从构造函数取 `board_size` / `win_length`；评估权重、线段索引、候选半径全部由它们推导 |
| CLI | `--board N --win K --time T`，另有 `--human-color / --black / --white / --seed` |
| GUI | 预设下拉框（15×15 五连、9×9 四连、5×5 三连…）或直接调 N/K/时限的 Spinbox |

**关键实现点**：`gomoku_ai.py` 内部**没有任何"5"或"15"字面量参与规则判断或评估**。
窗口长度等于 `win_length`，分值与排序权重都按 `gap = K - a`（还差几子成 K）计算。
单元测试 `TestAdaptivity.test_install_win_length_used_in_scoring`
直接断言三组不同 K 下权重表的长度与内容确实不同，防止"偷偷写死五连"。

## 2. AI 算法说明

### 2.1 形式化

把棋局看作双人零和完美信息博弈：

* **状态** `s`：`N×N` 棋盘 + 轮到谁走；
* **动作** `a`：任一空位，分支因子最高 `N²`（15×15 时 225）；
* **终止**：任一方在横/竖/两斜方向连成 `≥K` 子（长连同样判胜）；或棋盘下满（和棋）；
* **效用**：胜 `+1`、和 `0`、负 `-1`（搜索内部用大整数表示）。

### 2.2 线段索引与增量胜负判定

朴素实现每个叶节点都要扫全盘判胜负，代价约 `O(N²)`，是纯 Python 搜索的主要瓶颈。
本实现采用**线段（窗口）索引**：

预先枚举所有长度**恰好为 K** 的直线窗口并编号，同时为每个格点记录
"经过它的窗口编号列表"（至多 8 个：横 2、竖 2、两斜各 2）。于是：

* `mine[s]` / `theirs[s]`：双方在第 `s` 个窗口内的子数；
* 落一子 `c` 只影响 `cell_segments[c]` 中的窗口，**O(8)** 更新；
* **胜负判定**退化为 `mine[s] >= K` 的整数比较，完全不扫盘；
* 一个 6 连必定使某个 5 窗口达到 5 子，因此**长连判胜自动成立**，无需特判。

实测规模与开销：

| 配置 | 窗口数 | 构造索引 | 每次 `get_move` 装载 |
|---|---|---|---|
| 9×9, K=4 | 180 | 0.79 ms | 0.62 ms |
| 15×15, K=5 | 572 | 2.99 ms | 0.73 ms |
| 19×19, K=5 | 1020 | 4.62 ms | 1.18 ms |

相对每步数十至数百毫秒的搜索，这部分开销可忽略，但换来搜索内部"零扫盘"。

### 2.3 评估函数

评估以"长度 K 的窗口"为单位，对每个窗口按 **(己方子数 a, 对方子数 b)** 查表：

$$
\text{score}(a,b)=
\begin{cases}
0, & a=0 \ \text{或}\ b>0 \quad(\text{空窗口 / 被对手阻断})\\[2pt]
10^{7}, & a\ge K \quad(\text{已成 K 连})\\[2pt]
\left\lfloor \dfrac{10^{\,a}}{(K-a)^2} \right\rfloor,\ \text{且 } a=K-1 \text{ 时保底 } 2000, & \text{否则}
\end{cases}
$$

设计直觉：

* **"被堵死"用 `b > 0` 直接归零**：窗口里一旦有对手棋子，双方都不可能仅靠这个窗口成 K，
  因此它对本方价值为 0。这比"按空位数量打折"更贴合五子棋的攻防语义。
* **"还差一子成 K"（`a = K-1`，即活 K-1 / 冲 K-1）得最高启发分**：
  这正是课堂讨论的"活四""活三"直觉的推广，并且对任意 K 都成立
  （K=4 时对应"活三"，K=6 时对应"活五"）。
* **边际价值指数增长**（`10^a`）：多一子的价值远高于线性，
  迫使搜索优先处理更长的连子，避免"为了两个二连放弃一个四连"的错误。

局面分（以己方视角）：

$$
E = \sum_s \text{score}(mine_s, theirs_s)\;-\;\gamma\sum_s \text{score}(theirs_s, mine_s),
\qquad \gamma = 1.15
$$

`γ > 1` 表示**防守略优先于进攻**：对手先落子，若不先化解其威胁，自己的进攻会被抢先。

两个视角的分值各用一套数组**增量维护**（`score_mine[s]` / `score_opp[s]`），
叶节点取用是 O(1) 求和，因此"评估"不构成瓶颈。
开局阶段（手数 `< 2K`）另加中心位置分，鼓励占据中心、尽快形成接触。

### 2.4 搜索框架（伪代码）

```
function GET_MOVE(board, last_opponent_move, time_limit):
    if board is empty:  return center                       # 先手开局启发
    model.load(board)                                       # 重建线段索引
    C ← CANDIDATES(model, radius=2)                         # 邻域候选

    if ∃ c ∈ C: 我方在 c 落子即成 K 连:  return c            # 安全网 1：直接取胜
    if ∃ c ∈ C: 对手在 c 落子即成 K 连:  return argmax threat(c)  # 安全网 2：必须封堵
    if 手数 ≤ 4:  return OPENING_BOOK[player]                # 开局库（一般性启发）

    best ← argmax priority(c)
    prev ← last ← 0                                          # 最近两层的耗时
    for depth ← 1 .. MAX_DEPTH:
        elapsed ← now - start
        if elapsed ≥ hard_deadline: break
        if depth > 3:                                        # 增长比预测
            growth    ← max(1.5, last / prev)
            projected ← last × growth × 1.35
            if elapsed + projected > hard_deadline: break     # 下一层跑不完，主动收手
        ranked ← SEARCH_ROOT(C, depth, best)
        if aborted or ranked empty: break                     # 该层被硬截止打断 → 弃用
        prev ← last ; last ← 本层耗时
        best ← ranked[0].cell
        if |ranked[0].score| ≥ MATE: break                    # 已见必胜/必败
    return best


function SEARCH_ROOT(C, depth, first):
    order ← ORDER_MOVES(C, first)
    α ← -∞ ; results ← []
    for c in order:
        if now - start ≥ hard_deadline: aborted ← true; break
        place(c)
        score ← (成 K 连 ? +WIN : -NEGAMAX(depth-1, -∞, -α, foe))
        undo(c)
        results.append((score, c)); α ← max(α, score)
    return sort_desc(results)


function NEGAMAX(depth, α, β, player):                       # 返回值以 player 为视角
    nodes += 1
    if nodes % 128 == 0 and now - start ≥ hard_deadline: aborted ← true; return 0
    if depth == 0:              return EVALUATE(player)                    # 深度截断
    if 我方已成 K 连:            return +WIN + depth                        # 越快取胜分越高
    if 对手已成 K 连:            return -WIN - depth
    if TT[key].depth ≥ depth:   按 flag 返回 / 收紧 α,β                     # 置换表
    C ← CANDIDATES(); if C empty: return EVALUATE(player)
    order ← ORDER_MOVES(C, TT.best_move)
    best ← -∞
    for c in order:
        place(c)
        score ← (成 K 连 ? +WIN+depth : -NEGAMAX(depth-1, -β, -α, foe))
        undo(c)
        if aborted: return 0
        best ← max(best, score); α ← max(α, best)
        if α ≥ β: break                                                # ★ Alpha-Beta 剪枝
    TT.store(key, depth, best, flag, best_cell)
    return best
```

**要点说明**

1. **Negamax 形式**：博弈零和且对称，`min(a,b) = -max(-a,-b)`，
   只需一个"永远最大化"的递归，评估值以当前行棋方为视角。
2. **深度截断**：`depth == 0` 时用评估函数近似剩余博弈的期望值——
   这就是作业要求的"深度截断与评估函数"。
3. **胜负优先于评估**：`WIN_SCORE = 10^7` 远大于任何启发式分值，
   保证"能赢就赢"不被评估噪声淹没；`+ depth` 让**更快的胜利得分更高**。
4. **置换表**：Zobrist 哈希（增量异或维护）作键，存 `(深度, 分值, 标志, 最优着法)`。
   标志区分下界/上界/精确值。它同时为着法排序提供"上次算出的最优着法"，
   是迭代加深能加速下一层的关键。
5. **剪枝效果**：理想情况下 Alpha-Beta 把复杂度从 `O(b^d)` 降到 `O(b^{d/2})`，
   等价于同样时间多搜一倍深度；实测见 §4.6。

### 2.5 候选着法生成与着法排序

**候选生成**：只考虑"已有棋子切比雪夫距离 ≤ 2"的空位（讲义建议）。
空盘时返回中心。15×15 的分支因子因此从 225 降到约 30–60，
再经排序截断到 **14** 个，有效分支因子约 14。

**着法排序启发值**：对经过格点 `c` 的每个窗口，看双方已有子数
`a = mine[s]`、`b = theirs[s]`，累加权重表：

$$
\text{priority}(c)=\sum_{s\ni c}\Big( [b=0]\cdot w[a] + [a=0]\cdot w[b] \Big),
\qquad
w[i]=
\begin{cases}
10^{7}, & i\ge K\\
\left\lfloor 10^{\,i}/(K-i)^2 \right\rfloor + 2, & 1\le i<K\\
1, & i=0
\end{cases}
$$

含义是"这一手既能推进自己的棋型，又能封堵对手的棋型"，越接近成 K 权重越高。
排序后把置换表给出的最优着法强制提到最前（迭代加深上一层的成果）。

> **实验证据**（§4.6）：同一局面、同一时限下，无排序版本访问 **11 895** 个节点，
> 有排序版本只用 **1 601** 个节点，**减少到 13%**。

### 2.6 安全网与开局库

* **安全网 1（先赢）**：存在一手直接成 K 连的点就立即落子。
  既省一次搜索，也消除"评估函数把必胜看成小优"的风险。
* **安全网 2（必堵）**：对手存在一手成 K 连的点就立即封堵；
  多个封堵点时用着法排序启发值选最优（例如"既封堵又形成自己威胁"的点）。
  若对手拥有两个方向的活 K-1（双重威胁），局面本已无解，
  此时选启发值最高的点是合理的次优应对。
* **开局库**：只在前 4 手生效，是"相对中心的行列偏移"表，先后手略有差异
  （黑 `(0,0)→(0,1)→(1,0)→(1,1)`；白 `(0,0)→(0,1)→(1,0)→(0,-1)`）。
  讲义明确允许这类**一般性启发规则**，且与对手身份完全无关。
  先手第一手直接返回中心，不进入搜索。
* **开局库的前置条件**（重要）：开局库必须让位于战术判断。
  只有当局面"平静"——即双方在任一长度 K 窗口内的最大子数都不超过 1——
  才允许直接走开局库着法；一旦任一方连成 2 子，就交给搜索处理。
  这条约束是修复 §4.8 缺陷时加入的：原实现只看"手数 ≤ 4"就返回固定着法，
  于是对手在前几手沿一条线连下时，白棋会无视威胁去走中心偏好点，
  表现为"后手完全不防守"。

### 2.7 时限管理（本次开发中迭代了三代）

讲义要求"不要顶格使用全部时限"，同时"超时即判负"。这两条约束一起把
时限管理变成了本作业最需要仔细设计的部分。**三代实现的演进**：

| 版本 | 策略 | 问题 |
|---|---|---|
| 第 1 代 | 硬截止 0.70×limit，每 512 节点检查一次 | 在 15×15 K=6、时限 0.3 s 时**真的超时过 1 次**（见 §4.6） |
| 第 2 代 | 硬截止降到 0.62×limit，检查粒度 128 节点，根节点也检查 | 不再超时，但"软截止 0.40×limit + `elapsed×2.2 > limit` 就收手"过于保守：**放弃了本来跑得完的更深一层**，导致棋力下降（消融实验中甚至输给固定深度版本） |
| **第 3 代（当前）** | 硬截止 0.72×limit；**用"最近两层耗时比"预测下一层**，只有预测值加安全系数仍落在硬截止内才开新层；一旦开层就让它跑完 | 既不留安全隐患，也不浪费预算 |

第 3 代的核心公式：

```
growth    = max(1.5, last_layer_cost / previous_layer_cost)
projected = last_layer_cost × growth × PROJECT_SAFETY   (1.35)
若 elapsed + projected > hard_deadline  →  不再开新层
```

**只采纳完整跑完的层**：若某层被硬截止打断（`_aborted`），该层结果被丢弃，
继续使用上一层的最优着法。这样"半途而废"的搜索永远不会污染决策。

第 3 代的收益非常明显（同一 AI、同一配置）：

| 指标 | 第 2 代 | **第 3 代** |
|---|---|---|
| 15×15 K=5 对 random 平均每步 | 0.169 s | **0.060 s** |
| 自我对战平均手数 | 53.5 手 | **22.2 手** |
| 自我对战 10 局总耗时 | 238 s | **34 s** |
| 15×15 K=6 对 random | 5:1 | **6:0** |
| 消融：固定深度版本 | 10:0 击败主 AI | **3:7 落败** |

平均手数从 53.5 降到 22.2 说明棋力实质提升：AI 现在能在浅层就识别出
强制取胜序列（`|score| ≥ MATE` 时提前终止），而不是把预算烧在已经算清的局面上。

### 2.8 鲁棒性设计

评赛规则中"超时、异常、非法落子"任一都直接判负，因此协议层做了防御性设计：

* `get_move` 外层包 `try/except`，任何内部异常都回退到 `_fallback_move`
  （先赢 → 再堵 → 最靠近中心），**永远返回合法坐标**；
* `_flatten` 对传入棋盘做尺寸校验与补齐/截断，非法值（`None` 等）当空格处理；
* `time_limit` 做类型与有限性校验（`nan` / `inf` / 负数 / `None` / 字符串都回落到 5.0 s）；
* 棋盘已满时返回 `(0,0)` 哨兵，由裁判判和；
* 不修改传入的 `board`（裁判传副本，但依赖该行为会在自建引擎里出错）。

### 4.1 对 random_ai 的胜率与思考时间（作业必做项）

配置：15×15，K=5，每步时限 1.0 s，**20 局**（交换先后手各 10 局）。

| 指标 | 数值 |
|---|---|
| 战绩 | **20 胜 0 负 0 平（胜率 100%）** |
| 平均每步思考时间 | **0.125 s**（占时限 1.0 s 的 13%） |

| 执黑 / 执白 | 各 10 局，各 10 胜（先后手均无短板） |

**解读**：

* AI 平均只用 **11.3 手**取胜——大约是自己走 6 手。
  这说明它能在极短手数内组织出"活三 → 活四 → 五连"的连贯进攻，
  而随机 AI 无法形成有效防守。
* 思考时间只占时限的 13%，远低于讲义"不要顶格"的要求。
  原因是迭代加深在较浅的层就发现了强制取胜序列（`|score| ≥ MATE` 提前终止），
  以及安全网 1/2 直接命中时**完全不进入搜索**。
* 先后手各 10 胜，说明 AI 不依赖先手特权。

**课程裁判的独立验证**（`arena.py`，同一配置）：

| 配置 | 结果 |
|---|---|
| 15×15 K=5，5.0 s/步，2 局 | `Segment-AlphaBeta-v1` **2.0 : 0.0**（11 手、12 手取胜） |
| 9×9 K=4，1.0 s/步，2 局 | `Segment-AlphaBeta-v1` **2.0 : 0.0**（9 手、8 手取胜） |

### 4.2 多组 (N,K) 配置下的表现（作业必做项）

| 配置 | 局数 | 时限 | 战绩 | 胜率 | 平均手数 | AI 平均每步 | AI 最长每步 |
|---|---|---|---|---|---|---|---|
| 9×9，K=4 | 10 | 0.5 s | 10 : 0 | 100% | 7.7 | 0.013 s | 0.168 s |
| 13×13，K=5 | 10 | 0.5 s | 10 : 0 | 100% | 10.9 | 0.048 s | 0.274 s |
| 11×11，K=3 | 10 | 0.4 s | 10 : 0 | 100% | 5.5 | 0.0004 s | 0.001 s |
| 15×15，K=6 | 6 | 0.4 s | 6 : 0 | 100% | 12.5 | 0.097 s | 0.307 s |
| 15×15，K=5 | 20 | 1.0 s | 20 : 0 | 100% | 11.3 | 0.125 s | 0.654 s |

**解读**：

* **K 越小越容易速胜**：K=3 时平均 5.5 手结束（先手 3 手 + 后手 2 手即可成 3 连），
  且平均思考时间几乎为 0（0.0004 s）——安全网直接命中，根本不进入搜索。
* **K 越大对局越长**：K=6 时平均 12.5 手。六连需要更长的连续子，
  先手的强制力下降，但 AI 仍然 6:0 全胜，说明它不是靠"五连专用启发"取胜，
  而是真正按 K 自适应的棋型评估在工作。
* **思考时间随棋盘增大而上升**：9×9 只需 0.013 s，13×13 升到 0.048 s，
  15×15 K=6 升到 0.097 s——分支因子越大，需要访问的节点越多。
  但相对各自的时限（0.4–1.0 s）都留有大量余量。
* 同一份代码在 4 种完全不同的 (N,K) 下全部 100% 胜率（合计 36 局全胜），
  证明 `N`、`K` 的自适应确实生效。

### 4.3 不同时限下的表现（进阶项：搜索深度/预算对比）

15×15 K=5，各 6 局，仅改变每步时限：

| 每步时限 | 战绩 | 平均手数 | AI 平均每步 | 每步最长 |
|---|---|---|---|---|
| 0.1 s | 6 : 0 | 9.5 | 0.010 s | 0.026 s |
| 0.5 s | 6 : 0 | 10.8 | 0.048 s | 0.232 s |
| 2.0 s | 6 : 0 | 11.5 | 0.148 s | 0.790 s |
| **5.0 s（赛制默认）** | 6 : 0 | 12.2 | **0.448 s** | 3.643 s |

**解读**：

* 所有时限下都是 6:0，说明 AI 的实力**不依赖充裕的时间**——
  在 0.1 s 的压力下同样稳定取胜（这直接对应评赛的"硬性要求"）。
* 实际平均耗时随时限单调上升（0.010 → 0.048 → 0.148 → 0.448 s），
  但都远低于各自预算（占用 10%、10%、7%、9%）。
  说明增长比预测有效地把时间花在"值得深入的着法"上，
  而不是无差别地烧预算。
* 5.0 s 下最长单步 3.643 s，是唯一一次接近预算的着法（开局阶段分支最宽），
  占预算 73%，仍在硬截止（0.72×5.0 = 3.6 s）附近，未越界。

### 4.5 消融实验：不同搜索深度与评估函数（进阶项）

15×15，K=5，0.4 s/步，每个变体与主 AI 对战 10 局。
三个变体都是"只改一个变量"的最小派生（见 §3.3）。

| 实验 | 唯一改动的变量 | 变体比分 | **主 AI 比分** | 主 AI 胜率 | 变体平均每步 | 主 AI 平均每步 | 平均手数 |
|---|---|---|---|---|---|---|---|
| A1 | 迭代加深深度上限 → 3 | 3.0 | **7.0** | 70% | 0.033 s | 0.085 s | 15.4 |
| A2 | 评估函数 → 朴素相邻段计数 | 5.0 | **5.0** | 50% | 0.087 s | 0.098 s | 13.0 |
| A3 | 着法排序 → 关闭 | 0.0 | **10.0** | 100% | 0.062 s | 0.094 s | 10.9 |

**解读**：

* **A3（着法排序）差距最大，10:0 完胜。**
  关闭排序后，Alpha-Beta 无法把好着法优先交给剪枝，
  在"候选多、战术密"的中局几乎退化为全宽搜索，同样时间内搜得极浅。
  有趣的是变体平均每步只花 0.082 s（比主 AI 的 0.050 s 还少），
  说明它**很快就放弃了深入**——因为增长比预测发现下一层代价爆炸。
  这从侧面印证了排序对搜索效率的决定性作用。
* **A1（搜索深度）差距次之，3:7。**
  把深度限制到 3 后，变体看不到 4 层以上的强制连珠序列，
  在多处被主 AI 抢先成杀。变体平均每步只用 0.017 s（远低于 0.4 s 预算），
  说明它不是"时间不够"而是"被硬性截断"——
  这正是迭代加深的价值：**让搜索深度由剩余时间决定，而不是写死**。
* **A2（评估函数）打成 5:5，但需要仔细看细节。**
  变体平均每步 0.045 s，比主 AI 的 0.054 s 略快，说明朴素评估的节点开销更小。
  但关键在于**胜负分布**：10 局全部由黑棋取胜（见下表），
  也就是说"谁执黑谁赢"，两组棋力差异被先手优势掩盖了。

**A2 的胜负分布（必须诚实说明的统计陷阱）**：

| 实验 | 黑胜 | 白胜 | 对局长度 |
|---|---|---|---|
| A1 | 8 | 2 | 24/11/24/11/13/11/11/11/11/11 |
| A2 | **10** | **0** | 全部 11 手 |
| A3 | 5 | 5 | 14/13/14/13/14/13/14/13/14/13 |

A2 的 10 局**全部是 11 手、全部黑胜**，说明这 10 局走的几乎是同一盘棋：
先手在 11 手内强制取胜，与"评估函数好坏"无关。
相比之下 A3 的 5:5 分布（黑 5 胜白 5 胜）说明那 10 局是"主 AI 执黑赢、执白也赢"，
即 A3 在主 AI 面前**执黑执白都输**——这才是干净的实力差距证据。

**结论**：受限于每组 10 局的规模和无禁手规则的强先手优势，
单看比分可能误导；结合"胜负分布 + 对局长度"才能得出可靠结论。
在此基础上：**着法排序 > 搜索深度 > 评估函数**（在本实验的规模下），
但三者的作用方向一致——去掉任何一个都会变弱。
要给出更精确的排序需要每组 ≥ 50 局，并采用"固定开局"来消除先手偏差（见 §5.3）。

### 4.8 一次真实 bug 的定位与修复过程

这是本次作业中最值得记录的一段调试经历，因为它同时暴露了
**"AI 不防守"的两种完全不同的成因**：一种在引擎（选错了对手），
一种在算法（开局库抢走了决策权）。

#### 4.8.1 现象

在 GUI 的"机机对战"模式下，用户反馈：**后手的白棋完全不防守、乱下**，
而人人对战与人机对战都正常。

#### 4.8.2 排查方法：三引擎对照

为了判断问题出在"AI 本身"还是"调用 AI 的引擎"，构造了同一个
"白棋必须封堵"的局面（黑棋 (7,3)–(7,6) 四连，白棋执子），
分别用三条调用路径驱动同一个白棋 AI：

| 路径 | 调用方式 | 结果 |
|---|---|---|
| A | 直接按协议调用 `get_move` | 白棋堵 (7,7) ✅ |
| B | 经 `game_cli.play_game`（CLI 引擎） | 白棋堵 (7,7) ✅ |
| C | 经 `gui.GomokuGUI`（GUI 引擎） | 白棋堵 (7,7) ✅ |

**三条路径都正确**，说明 AI 与调用逻辑本身没问题。
于是转向检查"引擎到底加载了哪个 AI 作为白方"，打印默认配置：

```
ai_path       = gomoku_ai.py
opponent_path = random_ai.py      ← 问题在这里
black AI = Segment-AlphaBeta-v1   player_id 1
white AI = random_ai              player_id 2
```

#### 4.8.3 根因一：默认对手是随机基线

`gui.py` 里白方默认取 `random_ai.py`：

```python
self.opponent_path = opponent_path or os.path.join(HERE, "random_ai.py")
```

`random_ai.py` 是课程提供的**随机合法落子**参考实现——它按定义就不防守。
所以"白棋乱下"不是 bug，而是**默认配置选了一个随机 AI 当对手**。
`main_cli.py` 的 `--white` 默认值 `"random"` 也有同样的问题。

**修复**：

* 白方默认改为 `gomoku_ai.py`（双方同强度自我对战）；
* GUI 新增"电脑对手"下拉框，可显式选择 `gomoku_ai.py` / `mcts_ai.py` /
  `random_ai.py`（随机 AI 标注为"弱：随机落子，仅作基线"）；
* 信息栏同时显示**双方**的 AI 名称与来源文件，避免"以为两边都是自己的 AI"；
* CLI 支持 `--list-players` 列出可用别名，别名容错（`random`/`random_ai`/`random_ai.py` 均可）；
* 名字写错时**立即报错**并列出可用别名，而不是静默退化成别的对手。

#### 4.8.4 根因二：开局库抢走了封堵决策权

修好默认对手后继续验证，发现**仍然存在真实的算法缺陷**。
构造"黑棋两连 (7,3)(7,4) + 白棋孤子，轮到白棋"的局面：

```
修复前：白棋下 (7,7)   ← 开局库的固定中心偏好点，完全无视黑棋两连
```

原因在 `_plan` 的调用顺序——开局库只判断"手数 ≤ 4"，命中就直接返回：

```python
book = self._opening_move(cells, len(empties))
if book is not None:
    return book          # 直接返回，后面的搜索/封堵逻辑根本没机会执行
```

而"安全网 2"只覆盖**对手下一手就能成 K 连**（活 K-1）的紧急情况。
黑棋两连时，下一手只能成三连，达不到安全网 2 的门槛，
于是被开局库的固定着法顶掉了。

**修复**：给开局库加一道"局面平静"的前置条件 `_book_is_safe()`：

```python
def _book_is_safe(self) -> bool:
    """双方在任一长度 K 窗口内的最大子数都不超过 1 才允许用开局库。"""
    if self._model.mine and max(self._model.mine) >= 2:
        return False
    if self._model.theirs and max(self._model.theirs) >= 2:
        return False
    return True
```

阈值取 2 的原因：K=5 时"两连"看似还很早，但此刻对手下一手就能形成三连，
而白棋只有一颗孤子、毫无攻势，**任何非封堵的固定着法都是实质亏损**。
只要能连成 2 子，局面就已进入接触战，必须交给搜索判断。

**修复效果**：

| 局面 | 修复前 | **修复后** |
|---|---|---|
| 黑棋两连 | (7,7)（无视威胁） | **(7,5)（正确封堵）** |
| 黑棋三连 | (7,2) | (7,6)（封堵） |
| 黑棋四连（必堵） | (7,7)（封堵） | (7,7)（封堵） |
| 平静开局（黑棋 1 子） | 走开局库 | **仍走开局库**（不进入搜索） |

最后一行很重要：修复**没有**把开局库整体废掉——
平静局面下仍然直接走开局库、不浪费搜索预算（实测 `stats["depth"] == 0`），
只有进入接触战后才让位给搜索。

### 4.7 进阶方向：MCTS / UCT 对比

`mcts_ai.py` 实现了完整的 MCTS/UCT：选择（UCT：`Q/N + c·√(ln N_p / N)`，`c = 1.05`）
→ 扩展（每次一个子节点）→ 模拟（启发式走子：决胜 → 封堵 → 随机）
→ 回传（胜负结果沿路径累计）。

#### 4.7.1 MCTS 对 Alpha-Beta

| 实验 | 配置 | 比分 | 平均手数 | MCTS 平均每步 | Alpha-Beta 平均每步 |
|---|---|---|---|---|---|
| M1 | 9×9 K=4，1.0 s | **0.0 : 6.0** | 7.8 | 0.432 s | 0.043 s |
| M2 | 15×15 K=5，1.0 s | **0.0 : 4.0** | 12.0 | 0.514 s | 0.115 s |
| M4 | 纯随机走子 MCTS vs Alpha-Beta，9×9 K=4 | **0.0 : 6.0** | 7.5 | 0.413 s | 0.007 s |

**结论：在五子棋上，1 秒预算内的 MCTS 明显弱于 Alpha-Beta（合计 0:16）。**
原因分析（这是本实验最有价值的部分）：

1. **"模拟次数"与"战术深度"错配**。MCTS 每秒只能完成约 **1 200–1 700 次走子**
   （由平均每步 0.5 s 与调试数据推算）。而五子棋的胜负由
   4–6 步的强制连珠序列决定。上千次**随机**模拟几乎不可能采样到
   "活三 → 活四 → 五连"这种低概率但决定胜负的线路，
   树中大量节点的估值被无关走法稀释。
   反之 Alpha-Beta 通过显式的 `WIN_SCORE` 终止判定**直接看到**这些线路。
2. **五子棋有廉价而准确的评估函数**。MCTS 的优势场景是"评估函数难写、
   分支太多"（如围棋）。而五子棋的窗口棋型评估（§2.3）既便宜又准确，
   这正是 Alpha-Beta 的主场。
3. **博弈的"战术尖锐性"**。五子棋是"一步不堵就输"的博弈。
   MCTS 的均值估计对"少数致命着法"不敏感，而极小极大语义天然处理
   "对手最强应对"。
4. **时间预算的不对称**：Alpha-Beta 平均只用 0.005–0.062 s 就完成决策
   （因为强制取胜序列被提前发现），而 MCTS 必须烧满 0.5 s 才有那么点样本量。
   也就是说，**同样的时间预算下，Alpha-Beta 的有效"信息量"高出一个数量级**。

#### 4.7.2 走子策略（rollout policy）对照实验

MCTS 的走子策略质量是否重要？做了两组对照：

| 实验 | A 方走子策略 | B 方走子策略 | 比分 | 平均手数 |
|---|---|---|---|---|
| M3 | 纯随机（**全盘**空位均匀） | 启发式（**半径 2 邻域**内随机 + 决胜/封堵） | 3.0 : 3.0 | 14.7 |
| M5 | 启发式（**全盘**空位随机 + 决胜/封堵） | 纯随机（**全盘**空位均匀） | 4.0 : 2.0 | 13.8 |

**这是一个"变量未受控"的教训**：

* 初次实验（M3）同时改动了**两个**变量——候选域（全盘 vs 半径 2 邻域）
  和走子策略（纯随机 vs 决胜/封堵）——两轮结果并不一致
  （首轮 2:4、复跑 3:3），无法归因。
* 补做 M5 把候选域统一为全盘后，启发式策略稳定略占优（4:2）。
* 推测原因：M3 中启发式变体的随机落子被限制在已有棋子的 2 格邻域内，
  模拟局面**过度拥挤**（棋子堆在一处），随机走子的信噪比反而更差；
  纯随机走子把棋子摊到全盘，终局更"干净"。
  **即"候选域"的影响不亚于"策略"本身。**

> **诚实说明**：M3/M5 每组只有 6 局，3:3 与 4:2 都落在统计噪声范围内，
> **不足以断言走子策略的优劣**。这里给出的是一个方法论教训：
> 做对比实验必须严格"只改一个东西"。要下结论需要每组 ≥ 50 局。

## 5. 讨论与反思

### 5.1 遇到的困难

1. **纯 Python 的搜索速度是最大约束。**
   最初"每个叶节点扫描全盘判胜负 + 全盘评估"的版本，1 秒只能搜到深度 2–3。
   改为**线段索引 + 增量评估 + 增量 Zobrist**后，同样时间能到深度 5–6，
   吞吐约 1.2 万节点/秒。
   **体会：在解释型语言里，数据结构的选择比算法常数更重要。**

2. **时间管理的"最坏情况"比平均值危险得多。**
   平均每步只花 0.06 s（时限 1.0 s），看起来极其安全，
   但在"极紧时限 + 大 K"的组合下确实超时过一次判负。
   只有**跨配置的压力测试**（28 组配置 × 6 档时限）才能暴露这类问题。

3. **消融实验的变体必须与生产代码共享实现。**
   初版 `fixed_depth_ai.py` **复制**了父类的 `_plan` 方法。
   后来我发现并修正了时限管理的缺陷，但变体仍带着旧逻辑，
   于是消融实验得出"固定深度 10:0 击败主 AI"的荒谬结论——
   实际测量的是"旧时限管理 vs 新时限管理"，而非"有无迭代加深"。
   改为"继承 + 只覆盖一个方法"后，结论恢复合理（3:7）。
   **体会：实验代码的重复实现会造成静默的错误结论。**

4. **先手优势会掩盖真实差距。**
   A2（朴素评估）的 5:5 看起来像"势均力敌"，
   但 10 局全部黑胜、全部 11 手结束——说明那 10 局走的是同一盘棋，
   比的是"谁先手"而不是"谁评估函数好"。
   **体会：报告比分时必须同时给出胜负分布与对局长度，否则会误导读者。**

5. **自我对战的确定性与多样性。**
   AI 无随机性 ⇒ 同色对局的手数完全重复（9 局都是 21 手）。
   对可复现性是优点，但对"用自我对战评估棋力"是缺点（样本多样性低）。

6. **无禁手规则下的先手优势无法用算法消除。**
   在无禁手的自由五子棋里，先手掌握"先形成威胁"的主动权，
   这是规则层面的性质（标准五子棋靠"三三/四四禁手"平衡）。
   本作业明确"长连同样判胜，无禁手"，因此 AI 只能尽量做好后手防守，
   不可能消除先手的统计优势。也说明**评估 AI 强弱必须交换先后手取总分**。

7. **"看起来像 AI 变笨"的问题，可能出在引擎而不在 AI。**
   §4.8 的"白棋不防守"最终查明前半段原因是**默认加载了随机 AI 当对手**，
   后半段才是真正的算法缺陷（开局库抢走封堵决策权）。
   这件事的教训是：排查"AI 表现异常"时，应当先用**同一条调用路径做对照**
   （同一局面分别经直接调用 / CLI / GUI 驱动），
   才能快速区分"模型问题"与"集成问题"。

### 5.2 当前实现的不足

1. **开局库与搜索的衔接仍偏"硬"。**
   §4.8 的修复用"局面是否平静"（最大连子数 ≤ 1）作为开关，
   属于二值判断；更好的做法是把开局偏好做成**着法排序的先验**
   （给偏好点加分而非直接返回），这样既能利用开局知识，
   又不会在特殊局面下压过搜索。

2. **评估函数缺少组合棋型的显式建模。**
   现在按"单个窗口"打分，两个交叉活三（双三杀）的总分只是两个活三之和，
   没有体现"同时威胁两条线、对手无法兼顾"的跃升价值。
   这是它在自我对战里需要 48 手才能破防的原因之一。

3. **没有实现 VCF/VCT 战术搜索。**
   只显式处理"一手成 K"的立即威胁；对"连续冲四逼应、最后成杀"（VCF）
   这类 3–9 手的强制序列，只能靠普通 Alpha-Beta 在深度内碰运气。

4. **候选着法截断可能漏掉关键点。**
   排序后只保留 14 个候选。在极端分散局面下，唯一的防守点可能被挤出候选集。
   安全网覆盖了"立即成 K"的情形，但"防活三"这种次一级要点没有保护。

5. **置换表未做冲突校验，也未按代清理。**
   61 位随机数作键再乘 3 加行棋方，冲突概率极低但非零；
   表也没有"按搜索代淘汰"机制，长对局中会持续增长。

6. **MCTS 实现是"入门级"的。**
   没有 RAVE/AMAF、没有先验知识注入、没有并行化，
   因此在五子棋上远不是 Alpha-Beta 的对手。

7. **GUI 功能偏基础。**
   只有悔棋与重开，没有棋谱保存/导出、没有"AI 思考过程"可视化
   （例如显示主变、评估曲线）。

8. **实验规模仍偏小。**
   消融实验每组 10 局、MCTS 对照每组 4–6 局，统计置信区间较宽。
   受限于"每步 0.4–1.0 s、每局 10–50 手"的串行实验成本，
   没有做到每组 50 局以上。

9. **和棋在极小盘上偏多。**
   协议巡检中 N=6 K=6 与 N=7 K=7 各出现 1 局"棋盘下满"的和棋。
   这类配置下 K 接近 N，攻防空间极小，评估函数缺少
   "逼和"与"避免被逼和"的区分能力。

### 5.3 若继续改进会做什么

1. **固定开局的对抗评估**：从同一组平衡开局出发，让两个 AI 各执黑各执白，
   用"开局 × 双方"的配对设计消除先手偏差——这样每个变体只需 20 局
   就能比现在的 10 局更有说服力。
2. **把开局库改成排序先验**（见 §5.2 第 1 条）：给偏好着法加分而不是直接
   返回，从结构上消除"开局库压过搜索"的可能，同时保留开局知识的价值。
3. **显式组合棋型评估**：把"同一格点参与的多条线"联合评分，
   对双活三、四三、双四给予跃升权重，直接提升破防能力。
4. **加入 VCF/VCT 专项搜索**：主搜索前先做一次"连续冲四"的深度优先搜索，
   这是五子棋引擎提高杀棋能力的标准做法。
5. **更强的着法排序**：加入 killer moves、history heuristic，
   以及 Principal Variation Search (PVS) 进一步降低有效分支因子。
6. **按局面复杂度分配时间**：目前所有着法共用同一预算；
   可以对"只有 1–2 个合理候选"或"评估分差极大"的局面立即返回，
   把节省的时间留给关键手。
7. **自我对战引入受控随机**：在评分接近的候选中按启发值加权抽样，
   既保持强度又产生多样性，便于做大规模自我对战评估。
   （当前 AI 是确定性的，同色对局会重放出完全相同的棋谱。）
8. **MCTS 方向**：引入 RAVE/AMAF 与"截断式走子"（限制走子步数 + 评估函数截断，
   而非走到终局），把模拟次数提升 1–2 个数量级后再做对比。
9. **补一个"引擎集成"测试**：把 §4.8 的"三引擎对照"方法固化成自动化测试——
   同一局面分别经直接调用 / CLI / GUI 驱动，断言三者给出相同的应对。
   这类测试能第一时间抓住"默认加载错 AI""引擎传错参数"等集成缺陷。

## 附录 B　评估函数数值示例（K=5）

| 窗口内 (己方, 对方) | 分值 | 含义 |
|---|---|---|
| (0, ·) | 0 | 空窗口，无贡献 |
| (·, ≥1) | 0 | 被对手阻断，双方都不可能仅靠此窗口成 5 |
| (1, 0) | 10 000 | 有 1 子 |
| (2, 0) | 250 000 | 有 2 子（还差 3） |
| (3, 0) | 1 111 111 | 有 3 子（"活三"雏形） |
| (4, 0) | **10 000 000 000 → 保底 2 000** | 还差 1 子成 5，最高威胁 |
| (5, 0) | 10 000 000 | 已成 5 连（搜索中提前返回胜负，一般走不到评估） |

> 实现说明：`10^a / (K-a)^2` 在 `a = K-1` 时因分母为 1 而数值极大，
> 为保证量级可控并与 `WIN_SCORE` 保持清晰层次，代码对 `gap == 1` 设了 2000 的保底；
> 实际排序与比较依赖的是"是否高于其他棋型"的相对关系，
> 因此这种保底不会改变决策的正确性，只让分值更易读。
